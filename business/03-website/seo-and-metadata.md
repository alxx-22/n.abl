# SEO and metadata

What the site tells a search engine, a social scraper and a browser today, what
it does not, and the decisions behind both. Recorded 2026-08-15.

Set expectations first. n.abl has no domain history, no inbound links and no
content beyond one marketing page. Search is not going to be a meaningful source
of work for a long time, and no amount of metadata changes that. The point of
this file is narrower and achievable: **when someone types the name, or a link
gets pasted into a message, the result should be correct and should look
deliberate.**

---

## What ships today

All of it is static, in `index.html:4-27`.

| Tag | Value |
|---|---|
| `charset` | UTF-8 |
| `viewport` | `width=device-width, initial-scale=1.0` |
| `theme-color` | `#0E0C0A` — the brand ground, so the mobile browser chrome matches the page |
| `<title>` | n.abl — Technology implementation for small business |
| `description` | 211 characters. Names the offer, the market, the four kinds of work and the pricing model. |
| `icon` | `/favicon.svg` — the drawn mark in a rounded espresso tile |
| `og:title` | n.abl — Tell us what's costing you. We build the fix. |
| `og:description` | A technology implementation partner for small businesses. We start with the problem, not the technology. Fixed prices, no retainers. |
| `og:type` | `website` |
| `og:url` | `https://nabl.agency/` |
| `og:image` | `https://nabl.agency/brand/og.png`, declared 1200 × 630 |
| `twitter:card` | `summary_large_image` |

Two font preloads (`SpaceGrotesk-latin.woff2`, `InterTight-latin.woff2`) and one
stylesheet (`/fonts/fonts.css`), all same-origin.

The title is 52 characters, which fits a search result. The description is 211,
which does not — a result snippet is usually cut around 155 to 160 characters,
so the last sentence, "Fixed prices, no retainers", will often be truncated
away. That sentence is one of the strongest things the business can say, so if
the description is ever rewritten, move it to the front.

The `<title>` and the `og:title` differ on purpose. A search result is a list,
where the reader is scanning for what a company does, so the title names the
category. A shared link is a card with an image, where the reader has already
been given context by whoever sent it, so the card carries the headline.

### The share card

`public/brand/og.png`, 301 KB, generated by `scripts/build-og.mjs` from the same
brand assets as the site: the drawn wordmark, the headline "Tell us what's
costing you. We build the fix", and the eyebrow "Technology implementation".

Regenerate it whenever the hero headline changes, or the card will show the old
promise to everyone who shares the link. It was last regenerated in the
repositioning commit.

## What is missing

Honest list, worst first.

### 1. There is no `robots.txt`, and `/team` is crawlable

`public/` contains no robots file. Meanwhile the footer carries two real anchors
into `/team` — the full stop in the copyright line, and the small square in the
corner. Both are hidden from a reader. Neither is hidden from a crawler.

So the internal team space and, by extension, the sales CRM can be discovered,
requested and potentially listed by any search engine that follows links.

This is a tidiness problem rather than a security one. The team space is behind
Supabase Auth and the CRM is behind the same, so an indexed URL would show a
sign-in screen, not data. But an internal tool turning up in a search for the
company name looks careless, and it advertises the attack surface.

**Fix:** add `public/robots.txt`, disallow `/team`, `/sales-intelligence` and
`/portal`, allow everything else, and point at the sitemap. Remember what a
disallow actually does: it asks well-behaved crawlers not to fetch the URL. It
is not access control, and it does not stop anyone reading the same links in the
page source.

### 2. Every route serves the home page's metadata

The SPA fallback in `netlify.toml` and `public/_redirects` returns the same
`index.html` for every path. React then decides what to render on the client.

So `/privacy`, `/terms` and `/cookies` all report, in the static HTML:

- the title "n.abl — Technology implementation for small business"
- the home page's description
- the home page's Open Graph card

Anything that renders JavaScript will eventually see the right page. Anything
that does not — most link-preview scrapers, and any crawler on its first, cheap
pass — sees the home page three times over. Only the CRM sets a title at
runtime, in `src/pages/Crm.jsx:283`, and that is for the browser tab rather than
for a crawler.

**Fix, in order of cost:**

1. Set `document.title` and the description per route from the components, the
   same way the CRM already does. Cheap, and fixes browser tabs, history and
   bookmarks immediately. Does nothing for scrapers that do not run JavaScript.
2. Add a `<link rel="canonical">` per route. Same mechanism, same limits, but it
   stops the four public URLs looking like duplicates of each other.
3. Prerender the four public routes at build time into real HTML files. This is
   the only option that genuinely fixes it, and it is a build-system change, not
   a copy change. Not worth doing for three legal pages that nobody searches for.

Recommendation: do 1 and 2 now, and leave 3 until there is a reason — a blog, a
service page per category, or anything else that is meant to be found.

### 3. There is no `sitemap.xml`

Four public URLs: `/`, `/privacy`, `/terms`, `/cookies`. A hand-written sitemap
takes ten minutes and needs no generator. It matters less than the robots file,
but the two are usually written together.

### 4. Smaller gaps

| Gap | Effect | Worth fixing? |
|---|---|---|
| No `og:site_name` | The card shows the URL where it could show the name | Yes, one line |
| No `og:image:alt` | The share image is unreadable to a screen-reader user | Yes, one line |
| No `twitter:title` / `twitter:description` | None. Twitter falls back to the `og:` tags. | No |
| `<html lang="en">` rather than `en-GB` | Negligible, but the copy is British English and the market is UK | Yes, one character change |
| No structured data (JSON-LD) | No `Organization` or `LocalBusiness` entity for the name to attach to | Later. It needs a settled trading address and contact details first. |
| `og.png` is 301 KB | Slow first render of the share card on a poor connection | No. It is fetched by the scraper, not the visitor. |

## Decisions that are deliberate, and should not be "fixed"

### There is no analytics

No Google Analytics, no Plausible, no Netlify Analytics, no tag manager. The
cookie policy says so plainly: "We use no advertising cookies, no analytics
cookies and no third-party tracking cookies… there is no consent banner because
there is nothing to consent to."

That claim is worth more than the data would be at this traffic. Adding
analytics later means adding a banner, updating three legal pages and giving up
a genuinely differentiating sentence. If it is ever added, it must be a
first-party, cookie-free tool, and the legal pages change in the same commit.

The cost is real: there is no measurement of whether the page works. At this
stage that question is answered by what people say on discovery calls.

### The fonts are self-hosted

Six `.woff2` files, 214 KB, served from `/fonts/`. Requesting them from Google
would disclose every visitor's IP address to a third party on page load, which
is a disclosable transfer under UK GDPR and needless when the files are small
enough to ship. `index.html:21-24` carries the reason in a comment so nobody
"optimises" them back onto a CDN.

### The Content Security Policy is strict

`netlify.toml` sets `script-src 'self'` and permits `connect-src` only to the
Supabase project and `api.web3forms.com`. No third-party origin is allowed for
scripts, styles or fonts.

This is a real constraint on anything marketing-shaped. A chat widget, a
tracking pixel, an embedded booking tool or a font from a CDN will be blocked by
the browser, and it will look like a bug rather than a policy. That is the
intended behaviour: it makes adding a third party a deliberate act with a commit
attached, not something that gets pasted into a page.

### The security headers are already in place

`X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`,
`X-Frame-Options: DENY`, HSTS for a year including subdomains, a
`Permissions-Policy` that denies camera, microphone, geolocation, payment, USB
and interest cohorts, and `Cross-Origin-Opener-Policy: same-origin`. HTTPS is
enforced by Netlify.

None of these are SEO features, but a search engine notices HTTPS and a
prospect's IT person notices the rest.

## The keywords question

Nobody searches for "technology implementation partner". They search for the
problem, or for a tool, or for a town: *automate invoices*, *Zapier consultant
Manchester*, *fix my spreadsheet*, *booking system for a small business*.

The current single page cannot rank for any of that, and stuffing it with terms
would wreck the copy for the readers who actually arrive. The honest position:

- The six category cards already use the vocabulary a business owner would type,
  which is the right instinct even if one page cannot compete on it.
- If search is ever meant to produce work, it needs a page per problem, each one
  a real piece of writing about that problem. That is a content commitment
  measured in months, and it should not be started until there is delivered work
  to write about.
- Until then, the site's job is to convert people who arrive from outreach, a
  referral or a conversation. Optimise for those readers, not for a crawler.

## The checklist, when metadata next gets touched

- [ ] `public/robots.txt`, disallowing `/team`, `/sales-intelligence`, `/portal`
- [ ] `public/sitemap.xml` with the four public URLs
- [ ] Per-route `document.title` and description
- [ ] `<link rel="canonical">` per public route
- [ ] `og:site_name` and `og:image:alt`
- [ ] `lang="en-GB"`
- [ ] Regenerate `og.png` if the hero headline has changed since the last build
